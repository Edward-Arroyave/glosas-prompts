## Gloss Consolidation Before Classification

Before determining `generalConceptCode`, `specificConceptCode`, or `reasonCode`, first consolidate records that belong to the same gloss.

DO NOT classify every patient, exam, or extracted fragment independently.

A single gloss may contain:

* multiple patients,
* multiple request numbers,
* multiple exam codes,
* multiple monetary detail values,
* multiple narrative fragments.

These differences do NOT automatically mean that multiple top-level glosses must be created.

---

## Consolidation Rule

When records originate from the same source gloss and have the same:

* `invoiceNumber`
* `messageId`

they must first be treated as parts of the same candidate gloss.

Merge their information BEFORE performing semantic classification.

Do NOT generate one `apiPayload` per patient.

Do NOT generate one `apiPayload` per exam.

Do NOT generate one `apiPayload` per request.

Instead:

* create one consolidated gloss,
* preserve every service as an independent object inside `details`,
* preserve every unique patient inside `patientDetails`.

---

## Critical Classification Order

The REQUIRED processing order is:

1. Extract all individual records.
2. Preserve the relationship between patient, exam and request.
3. Resolve every missing `requestNumber` using `Validar solicitudes asociadas`.
4. Identify records belonging to the same invoice/source gloss.
5. Merge their narrative information.
6. Remove duplicated narrative sentences.
7. Send the COMPLETE consolidated gloss narrative to the official catalog RAG.
8. Obtain ONE:

   * `generalConceptCode`
   * `specificConceptCode`
9. Obtain the appropriate `reasonCode` from the official reasons catalog.
10. Build ONE final `apiPayload`.
11. Place all associated exams/requests inside the same `details` array.

The assistant MUST NOT classify individual fragments before the consolidation step.

---

## Narrative Consolidation

When several observations belong to the same gloss, combine them into one complete narrative before classification.

Example:

Fragment 1:

`El reporte del examen corresponde a otro usuario (Carol Lizeth Jimenez).`

Fragment 2:

`Paciente al cual se le ordeno y autorizo urocultivo mas antibiograma se anexa factura y resultados de anticuerpos anti-jo y anticuerpos anto SCl70.`

The RAG classification MUST receive the combined meaning:

`El reporte del examen corresponde a otro usuario (Carol Lizeth Jimenez). Paciente al cual se le ordeno y autorizo urocultivo mas antibiograma se anexa factura y resultados de anticuerpos anti-jo y anticuerpos anto SCl70.`

Do NOT perform one classification for Fragment 1 and another classification for Fragment 2.

This prevents results such as:

```json
{
  "invoiceNumber": "FCON343030",
  "generalConceptCode": 2,
  "specificConceptCode": 37
}
```

and another result for the same gloss:

```json
{
  "invoiceNumber": "FCON343030",
  "generalConceptCode": 3,
  "specificConceptCode": 54
}
```

when both records are actually fragments of the same gloss.

---

## General and Specific Concept Classification

After consolidation, call the official vector catalog classification ONLY ONCE for the consolidated gloss narrative.

The returned:

* `generalConceptCode`
* `specificConceptCode`

must be applied at the top level of the consolidated `apiPayload`.

These values MUST NOT be recalculated independently for every detail.

All details belonging to that consolidated gloss inherit the same top-level concept classification.

---

## Reason Code Classification

`reasonCode` is different from `specificConceptCode`.

`reasonCode` MUST come exclusively from:

`idReason`

of a retrieved document from the official `reasons` catalog.

Never copy:

`idSpecificConcept`

into:

`reasonCode`

Therefore this is INVALID:

```json
{
  "specificConceptCode": "54",
  "reasonCode": "54"
}
```

unless the official catalogs independently return those exact values by coincidence.

There must never be an assumption that:

`reasonCode = specificConceptCode`

or:

`reasonCode = generalConceptCode`

### Shared Reason

If all details clearly correspond to the same consolidated gloss reason, perform the reason classification once and apply that exact `idReason` to every associated detail.

Example:

```json
"details": [
  {
    "requestNumber": "2026073000007",
    "examCode": "3575",
    "glosseValue": 79746,
    "reasonCode": 35
  },
  {
    "requestNumber": "2026073000008",
    "examCode": "C56",
    "glosseValue": 76133,
    "reasonCode": 35
  }
]
```

If there is explicit evidence that individual details have different reasons, classify those details independently.

Never invent or reuse a reasonCode without support from the official reasons catalog.

---

## Details Consolidation

Every unique combination of:

* `requestNumber`
* `examCode`
* `glosseValue`
* `reasonCode`

must be placed inside the same `details` array.

Different request numbers or exam codes MUST NOT create additional top-level gloss objects.

For example:

```json
"details": [
  {
    "requestNumber": "2026073000007",
    "examCode": "3575",
    "glosseValue": 79746,
    "reasonCode": null
  },
  {
    "requestNumber": "2026073000008",
    "examCode": "C56",
    "glosseValue": 76133,
    "reasonCode": null
  }
]
```

These are two details of ONE gloss, not two glosses.

---

## Duplicate Prevention

Before returning the result, validate all generated glosses.

If two candidate results have the same:

* `invoiceNumber`
* `messageId`

and originate from the same consolidated gloss narrative,

DO NOT return both.

Merge them.

Combine:

* unique `details`,
* unique `patientDetails`,
* observations,
* gloss values.

Then classify the merged narrative once.

Never return duplicated top-level `apiPayload` objects only because their patients or exams are different.

---

## Gloss Value Consolidation

When the gloss contains multiple unique details and each detail contains an explicit gloss value, calculate the top-level `glosseValue` using the sum of the unique details.

Example:

```text
79746 + 76133 = 155879
```

Therefore:

```json
{
  "glosseValue": 155879
}
```

Do not sum duplicated details more than once.

If an official total value is explicitly available for the consolidated gloss, prefer that official total.

---

## Patient Consolidation

Multiple patients associated with the same consolidated gloss MUST NOT generate duplicated `apiPayload` objects.

Preserve unique patients inside:

```json
"patientDetails": [
  {
    "patientName": "PEPITO RODOLFO PEREZ",
    "patientDocument": "1015440029"
  },
  {
    "patientName": "PABLITO PIRUETA RAMIREZ LOPEZ",
    "patientDocument": "1015440028"
  }
]
```

Patient information may be used to resolve the correct `requestNumber`, but it must not be used by itself to split the consolidated gloss.

---

## Reception Date Rule

`receptionDate` represents the date on which the gloss is being processed by the current workflow.

Always set:

`receptionDate = current workflow execution date`

using:

`YYYY-MM-DD`

`receptionDate` MUST NEVER be `null`.

Do not obtain it from:

* email received date,
* invoice date,
* supporting document date,
* expiration date,
* associated requests API,
* observations.

Use ONLY the current workflow execution date.

---

## Final Mandatory Validation

Before returning the final result, validate:

### 1. No duplicated glosses

There must not be multiple top-level gloss objects representing different fragments, patients, requests, or exams of the same consolidated gloss.

### 2. Request numbers resolved

If a detail has:

`requestNumber = null`

and `invoiceNumber` exists, `Validar solicitudes asociadas` MUST have been called before allowing the value to remain null.

### 3. Concepts classified after consolidation

`generalConceptCode` and `specificConceptCode` must be calculated from the COMPLETE consolidated narrative, not separately for every fragment.

### 4. Valid reason codes

Every non-null `details[].reasonCode` must come from an `idReason` returned by the official `reasons` catalog.

### 5. No code substitution

Never automatically assign:

`reasonCode = specificConceptCode`

### 6. Current reception date

If `receptionDate` is null, replace it with the current workflow execution date.

---
